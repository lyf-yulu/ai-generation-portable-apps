# 产品升级评审 · 2026-08-14

以产品经理视角对 AI 生成聚合平台做的一次现状盘点与升级建议。所有结论基于本机实测，不基于 CLAUDE.md 快照（快照已多处过期，见附录）。

---

## 一、你现在做的是什么产品

摸完数据后，这个项目的真实定位比「工具集合」更清晰：

**它是一家公司内部的 AI 生成中台。** 30 个注册账号、近两周 13 人活跃、每天 200+ 次生成任务、累计产出 31G 素材。这已经不是「自己写的小工具」，而是有真实用户依赖、停机会被投诉的内部服务。

这个判断决定了后面所有优先级：**能力已经够多了，缺的是「运营一个服务」所需要的东西**。

### 真实使用画像（近 14 天）

| 子应用 | 产出量（张/秒） | 每日任务数 | 状态 |
|---|---|---|---|
| Seedance（视频） | 10249 秒 | 18–117 | 主力 |
| 人像生成（Volcengine） | 9331 秒 | 30–95 | 主力 |
| 图像生成（Nano Banana） | 918 张 | 21–108 | 主力 |
| Dreamina | 276 | 0–2 | **接近废弃** |
| 飞书任务 Agent | — | 未计入 | 新增长点 |

**产品判断**：三个主力应用形成了稳定的日常工作流。Dreamina 每天 0–2 个任务，是明确的长尾——它却占着 2964 行代码（全项目最长的 app.py）和一套独有的双守卫权限机制、双前端兼容负担。

## 二、被低估的现状（做得比想象中好的地方）

盘点时发现几处架构其实已经很成熟，做升级规划时不该重做：

1. **子应用注册已配置化**。`portal/apps.json` 驱动一切——加一个子应用真的只要一条 JSON（端口、挂载方式、颜色、计量单位、统计合并策略都在里面）。这是很干净的插件化设计。
2. **FastAPI 迁移已在生产运行**。四个子应用全部跑 uvicorn，只有 Portal 自己还是 stdlib。且 FastAPI 版是 `import app as legacy` 的**薄壳**，业务逻辑仍在 `app.py` 里——所以改 `app.py` 依然生效，没有双份代码漂移的风险。
3. **真正的 RBAC 已落地**。三角色 + 权限位（`portal/app.py:138`），不是布尔 admin 标志。
4. **飞书 Agent 是最大的隐藏资产**。23433 行、LangGraph 12 节点、断电续跑、幂等提交、人工审批中断——它的工程完整度远超四个子应用，且已挂进 Portal 成为第五个 tab。

## 三、核心短板：你有一个「生成平台」，但没有「运营后台」

这是我认为最值得投入的一块，三个问题互相关联。

### 3.1 花钱这件事完全是黑盒

**实测**：全项目 grep `quota` / `cost` / `price` / `billing` —— **零命中**。

意味着：
- 不知道每个同事花了多少钱，只知道产出了多少张/多少秒
- 没有配额，任何人可以无限提交（一个手滑的批量任务就能烧掉预算）
- 没有失败成本核算——统计只记 `jobs` 提交数，**不记成功/失败**（`daily` 里只有 `requests` 和 `jobs` 两个字段）。而生成失败同样烧钱

**为什么这是第一优先级**：视频生成单价不低，13 个活跃用户每天 200+ 任务。现在这笔钱花得对不对、有没有人在浪费，你无法回答。上公网给外部客户时，这是绝对的 Blocker。

**建议做法**：
- `apps.json` 里已有 `metrics` / `unit_label` / `stats_combine` 字段——顺着这个思路加 `unit_price`，成本核算就能复用现有的统计管道
- 任务落库时记 `status`（success/failed/cancelled）和 `retry_count`
- 统计页加「本月花费」「失败率」「人均成本」三个数
- 配额做成软限制先跑：超额只提示不拦截，观察一个月再决定要不要硬拦

### 3.2 原始使用明细留存不到 5 分钟

**实测**：`portal/app.py:936-938` 把**每一个 HTTP 请求**都写进 `records`，包括前端每 5 秒一次的 `/api/jobs` 轮询。上限 1000 条，超过 2000 截断。

今天 8 万+ 请求量下的实际后果：`records` 里最早的记录是 13:25，最新 13:29 —— **只剩 4 分钟**。

```
记录字段：time, app, ip, method, path, username
今日请求量：feishu-agent 22693 + nano-banana 18541 + seedance 16581 + ...
```

聚合数据（`daily` / `by_user`）是完好的，但凡是需要查明细的场景全部失效：「昨天下午谁把 seedance 打满了」「这个失败任务是谁提的」——查不了。

**建议做法**：轮询类 GET 不入 `records`（只记任务创建等有业务含义的事件），量会掉两个数量级，再把上限提到几万条即可覆盖数周。

### 3.3 数据资产在膨胀但没人管

- 仓库已 **31G**（seedance 5.8G + nano-banana 2.0G + agent 254M…），磁盘剩 80G
- `feishu-generation-agent.log` 已 **108MB**，且全项目 grep `RotatingFileHandler` / `logrotate` —— 零命中，**无日志轮转**
- `tools/` 下有 `cleanup_old_media.py`、`cleanup_server.py`，但没有定时任务在跑（LaunchAgents 里没有清理服务）

**建议做法**：日志轮转（launchd + newsyslog 或直接用 Python `RotatingFileHandler`）；产出文件加保留策略（比如 90 天前的自动归档/清理，飞书表格已有归档兜底）；统计页加一个磁盘水位提示。

## 四、前端升级建议

现状：`app.js` 2092 行 + `index.html` 880 行 + `styles.css` 831 行，PetiteVue，7 个 tab（3 个 iframe + 2 个原生组件 + 密钥库 + 统计）。响应式断点是有的（6 处 `@media`），`viewport` 也有。

### 4.1 最高价值：跨应用的统一产出库

**现状**：历史记录只有 Dreamina 内部有（`index.html:246` 的「历史」子 tab）。其他四个应用产出的东西，用完就散在各自 `outputs/` 里。

**问题**：同事昨天生成的那张图想再用，得回忆是在哪个 tab 做的，然后在那个 tab 里翻。31G 素材实际上是**不可检索的**。

**建议**：加一个「我的产出」tab —— 跨应用、按时间倒序、缩略图墙、按应用/类型/日期筛选、点击看参数、一键复用参数重生成。这是把 31G 沉睡数据变成资产的关键一步，也是同事感知最直接的功能。

技术上不难：各子应用已有 `job_owners`（4099 条映射）和统一的下载 token 机制。

### 4.2 能力落差：好东西只有一个应用有

盘完发现几处明显的「A 有 B 没有」，补齐就是低成本高感知的升级：

| 能力 | 现状 | 建议 |
|---|---|---|
| **AI 提示词优化** | 只有 seedance 有（DeepSeek + 229 行 SKILL.md） | 图像类应用同样需要，抽成 Portal 级公共服务 |
| **多标签工作区** | 只有 seedance / nano-banana 有 | 人像生成、Dreamina 缺失 |
| **历史记录** | 只有 Dreamina 有 | 见 4.1，统一做 |
| **toast 提示** | 只有 Dreamina 局部有（`dm-hist-toast`） | 全局统一反馈组件 |

### 4.3 体验细节

- **深色模式**：grep `prefers-color-scheme` 零命中。同事白天用得多，优先级不高，但成本也低
- **任务队列可视化**：现在提交后靠 5 秒轮询刷状态，没有「我排在第几个/预计还要多久」。视频生成动辄几分钟，这个焦虑感很实在
- **移动端**：断点有了，但 iframe 里的子应用是 `height:calc(100vh - 48px)` 固定，手机上体验待实测

## 五、技术债（会挡住未来的）

### 5.1 `cgi` 模块 = Python 3.13 硬 Blocker

`cgi` 在 Python 3.13 已移除，而它**深度渗透在业务函数签名里**——seedance/nano-banana/volcengine 三个 app.py 的十几处函数都以 `form: cgi.FieldStorage` 为参数类型。

**好消息**：FastAPI 壳里已经有 `_FormShim` 适配层（`seedance/app_fastapi.py:130`），意味着迁移路径已铺好——只需把 legacy 函数的类型注解和取值方式换掉，不用重写解析逻辑。成本比看起来低。

### 5.2 Dreamina 的存在感与维护成本不匹配

2964 行代码、双前端兼容负担（Portal 发 FormData / 独立前端发 JSON）、双守卫权限机制，换来每天 0–2 个任务。

**产品决策建议**：明确它的去向——要么下线（保留数据、移除 tab），要么合并进其他应用。继续维持现状是持续的隐性成本，每次全局改动都要多测一个应用。

### 5.3 外网通道状态与文档不符（需你确认）

**实测**：`com.ai-portal-tunnel` 正在运行，`cloudflared tunnel --url http://127.0.0.1:9090` 进程活跃（PID 91934，从周三起）。

但 CLAUDE.md 写的是「cloudflared 已 unload，改走局域网 HTTPS」。

**为什么要提**：这是 quick tunnel（随机 `trycloudflare.com` 域名），意味着服务当前**对公网可达**。配合上面提到的「无配额、无成本核算、密钥库在里面」，这个暴露面值得你确认是有意开启还是遗留。如果是有意的，那 3.1 的配额和 `X-Is-Admin` 明文签名问题（`docs/security-hardening-v2-plan.md` 1b 条，实测 grep `internal_secret` 零命中，**未修**）优先级要往上提。

## 六、建议的优先级排序

我按「用户感知 × 风险 ÷ 成本」排，不按技术兴趣排：

**P0 — 先做，因为涉及钱和风险**
1. 成本核算 + 失败率统计（顺 `apps.json` 的 metrics 管道扩展）
2. 确认外网通道意图；若保留则修 `X-Is-Admin` HMAC 签名
3. 修 `records` 污染，让明细可查
4. 日志轮转 + 产出保留策略

**P1 — 同事感知最强**
5. 跨应用统一产出库（「我的产出」tab）
6. 提示词优化提升为 Portal 公共能力
7. 任务队列可视化（排队位置 + 预计时间）
8. 软配额（先只提示）

**P2 — 结构性**
9. 飞书 Super Agent P1–P5（已有完整 plan，是最大增长点）
10. `cgi` 迁移（复用已有 `_FormShim`）
11. Dreamina 去向决策

**P3 — 锦上添花**
12. 深色模式、全局 toast、移动端实测
