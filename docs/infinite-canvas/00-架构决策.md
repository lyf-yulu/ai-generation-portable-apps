## 1. 决策摘要

**复用**：`~/ai-creation-canvas/web/` 的 React 无限画布前端（约 7700 行 TSX）。
**不复用**：`~/ai-creation-canvas/server/` 的 Python 后端。
**新写**：`infinite-canvas/` 薄后端（FastAPI），含契约翻译层，把画布的生成请求转发到现有 seedance / nano-banana。

生成链路：

```
浏览器 (Portal 已登录)
  │  iframe src=/infinite-canvas/index.html
  ▼
Portal 9090 (HTTPS, 自签)
  │  _try_proxy 剥掉 /infinite-canvas 前缀
  │  注入 X-Username / X-Portal-User-Id / X-Is-Admin / X-Portal-Ts / X-Portal-Sig
  ▼
infinite-canvas 8893 (FastAPI, 127.0.0.1)
  ├── /api/v1/session      ← 由 Portal 签名头合成，前端零改动即可通过 AuthGate
  ├── /api/v1/projects*    ← 画布存档（SQLite，一张表存一个 JSON blob）
  ├── /api/v1/assets*      ← 用户上传素材
  ├── /api/v1/models       ← 由 seedance/nano-banana 的 /api/config 翻译而来
  └── /api/v1/jobs         ← ★契约翻译层
        │
        ├── image.generate / image.edit ──► nano-banana 8797
        └── video.* ────────────────────► seedance 8787
                                             │ 现有 Key、现有 providers.json
                                             ▼
                                          火山 / T8Star
```

统计：翻译层在创建任务时回吐 `X-Job-Id` 响应头，Portal 代理据此登记；Portal 轮询 `GET /api/jobs/{id}` 时由翻译层如实上报 `task_type` 与 `done`/`duration`，图片按张、视频按秒分别计入。

## 2. 为什么不复用 canvas 的 Python 后端

三条独立理由，任一条都足以否决：

### 2.1 我们选的方案 B 恰好丢弃了它的主体

canvas 后端 2373 行的 `storage/sqlite.py` + `app.py` + `adapters/` + `model_routing.py` + `credential_pools.py`，绝大部分服务于「模型注册表 / 线路 / 分组凭据池 / 管理员派发 / 独立用量计费」。方案 B 明确要把这些统一回 Portal，等于把它 80% 的代码接进来又停用。

真正要保留的只有 `canvas_projects` 一张表：

```sql
CREATE TABLE canvas_projects (
    project_id TEXT NOT NULL, user_id TEXT NOT NULL,
    title TEXT NOT NULL, document_json TEXT NOT NULL,
    version INTEGER NOT NULL, created_at TEXT NOT NULL, updated_at TEXT NOT NULL,
    PRIMARY KEY(user_id, project_id)
)
```
（`server/ai_creation_canvas/storage/sqlite.py:368-373`）

一张表、一个 JSON blob、乐观锁一个整数版本号。重写约 300 行，比阉割 2373 行便宜得多。

### 2.2 它有硬编码守卫会主动拒绝我们的部署形态

`server/ai_creation_canvas/config.py:18`：

```python
_PRODUCTION_REPOSITORY = Path("/Users/260413a/ai-generation-portable-apps")
```

非 production 配置**不允许**把 data_dir 放进这个仓库（`config.py:146-147`）；而 production 模式又强制要求 Redis、凭据池 JSON、`--trusted-host 127.0.0.1`、≥32 字节 `AICC_CREDENTIAL_HMAC_KEY`（`app.py:142-145,195-196`）。另有 `_PRODUCTION_PORTS = {9090, 8787, 8797, 8891, 8991}` 端口拒绝名单（`config.py:17`）。

这些守卫是那个项目**为自己的独立部署边界**设的，不是 bug。把它嵌进本仓库就是在跟它的设计意图搏斗，每次上游更新都要重打补丁。

### 2.3 与本仓库既有约定不一致

本仓库 5 个子应用是同一套模式：`<dir>/app.py`（+ 可选 `app_fastapi.py`）、`X-Job-Id` 响应头、`/api/jobs/{id}` 状态、`report_final_to_portal()` 回调、`_verify_portal_sig()` 验签。新后端照这套写，维护心智负担为零；接 canvas 那套则引入第二套完全不同的分层（domain / adapters / routing / coordination）。

> **结论**：我们复用的「轮子」是那 7700 行画布交互本体——它才是真正难写、有价值的部分。它的 Python 安全内核服务于另一种部署模型，不是我们的轮子。

## 3. 关键事实（已实测核实，不是推断）

### 3.1 Portal 侧

| 事实 | 位置 |
|---|---|
| 子应用注册是**声明式**的，`portal/apps.json` 加一条即可，后端零改动 | `portal/app_spec.py:36-71` |
| 代理会**剥掉** `/<name>` 前缀再转发 | `portal/app.py:1973` |
| 已原生支持 FastAPI 子应用：`<NAME>_ENGINE=fastapi` + `<dir>/app_fastapi.py` + **仓库根共享 `.venv`** | `portal/app.py:641-657` |
| 共享 `.venv` 已装 fastapi 0.139 / uvicorn 0.51 / httpx / pydantic / python-multipart / PyYAML | 实测 `pip list` |
| 请求头是**白名单**，Cookie 与自定义头一律丢弃 | `portal/app.py:2015-2020` |
| 注入身份头，签名为 `HMAC-SHA256(INTERNAL_TOKEN, "{ts}:{is_admin}:{username_pct_encoded}")` | `portal/app.py:129-136, 2059-2084` |
| `X-Username` 是 **percent-encoded**，子应用需 `unquote` | `portal/app.py:2058-2060` |
| 仅 `.html/.js/.css/.mjs` 强制 no-cache；`.wasm/.json/.svg/.woff2` **不在列** | `portal/app.py:2125` |
| 下行真流式（64KB 块）、支持 Range；上行整读进内存，上限 200MB | `portal/app.py:2103-2129, 1293` |
| **完全不支持 WebSocket**；SSE 因 64KB 阻塞读实际不可用 | 全文无 `Upgrade`/`101` 处理 |
| 看门狗每 15s 探活，连续 3 次失败即重启 | `portal/app.py:685-715` |

### 3.2 统计链路（CRITICAL）

`_is_job_request()` 是**硬编码路径白名单**（`portal/app.py:1101-1107`），当前不含 `/api/v1/jobs` —— **必须追加**，否则统计全程静默不生效。

登记条件（三者缺一不可，`portal/app.py:2093-2097`）：
1. 路径命中白名单且方法为 POST
2. 响应状态是 **200 或 201**（202 不行）
3. 响应头带非空 **`X-Job-Id`**

轮询（`portal/app.py:975-1045`）：每 15s 请求子应用 `GET /api/jobs/{id}`（**注意不带 `/v1`**），读顶层 `status`（终态 `succeeded`/`failed`/`completed`）、`done`、`task_type`、`duration`。2 小时未终态则丢弃。

**关键发现——`task_type` 可以覆盖注册时的类型**（`portal/app.py:1017-1022`）：

```python
task_type = (data.get("task_type") or nested.get("task_type") or "").lower()
job_type = job["job_type"]
if "video" in task_type or "frame" in task_type:
    job_type = "video"
elif "text2image" in task_type or "image2image" in task_type:
    job_type = "image"
```

这解决了「画布一个应用同时出图和出视频、而 Portal 只按路径分类」的难题：翻译层在 `/api/jobs/{id}` 里如实上报 `task_type` 即可被正确分流计数。

`done` 必须是**真实产出件数**，纯失败报 0。**严禁** `max(1, ...)` 兜底——注释 `portal/app.py:1003-1010` 明确警告这会制造幽灵计数。

## 4. 已知必须处理的坑

| # | 坑 | 影响 | 对策 |
|---|---|---|---|
| 1 | Portal 不转发 Cookie；canvas 前端 `credentials:"same-origin"` 但服务端不能依赖 Cookie | 会话必须完全由签名头合成 | 新后端不用 Cookie，身份只认 `X-Portal-*` |
| 2 | `X-CSRF-Token` 不在 Portal 白名单 | 任何 CSRF 校验都会失败 | 新后端不做 CSRF（同源 iframe + 签名头 + 仅回环监听即边界） |
| 3 | API 前缀锁死 `/api/v1/`，但浏览器地址是 `/infinite-canvas/api/v1/...` | 不改会打到 Portal 根，404 | 改 `client.ts:3` 为 `${import.meta.env.BASE_URL}api/v1/` 并同步放宽 `safeApiPath` |
| 4 | 路由无 `basename`，路由表写死 `/canvas` `/tasks` 等 | 刷新页面 404 | `createBrowserRouter(routes, {basename: import.meta.env.BASE_URL})` |
| 5 | 内联样式 `mask: "url(/logo.svg) ..."` 不被 Vite 重写 | 图标裂 | 插值 `import.meta.env.BASE_URL`（`web/src/components/layout/app-top-nav.tsx:42-43`） |
| 6 | `X-Portal-User-Id` **不参与** Portal 的 HMAC 签名 | 理论上可被持有 token 者篡改归属 | 接受（伪造仍需 INTERNAL_TOKEN，与现有 5 个子应用同一信任级别）；记为后续可加固项 |
| 7 | 画布节点存的是同源 API 路径而非 blob | 换后端会让历史画布的图/视频失效 | 首次上线无历史数据；结果 URL 一律走我们自己的 `/api/v1/results/*` 稳定路径 |
| 8 | Portal 看门狗 45s 内探活失败即重启 | FastAPI 冷启动慢会被反复杀 | 启动路径不做重活（不预热模型目录，懒加载） |
| 9 | `Start All.command` 端口列表已漏 8891 | 停旧实例阶段漏杀 | 顺手补 8891 + 8893 |
| 10 | AGPL-3.0 | 前端代码来自 AGPL 项目 | 保留 `LICENSE` 与来源说明；本仓库仅内网自用，不对外分发二进制 |
